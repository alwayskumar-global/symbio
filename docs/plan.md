# Symbio implementation plan

**Build a documented reconstruction of Kalundborg immediately before the local biogas addition.** The demonstration should start with residues already serving agricultural uses, discover the missing energy-recovery capability, and calculate whether adding it can deliver usable energy while honoring existing commitments. A successful demo can conclude that a candidate is valuable, tied with the baseline, conditional on a specific agreement, or infeasible. The calculation determines which.

The first implementation milestone should prove one complete vertical slice from a Relate query through an allocation solve to a saved, inspectable explanation. That establishes the central technical claim before investing in a larger dataset or frontend.

## 3. Architecture, graph and discovery

Use **FastAPI/Pydantic → one embedded Relate owner → deterministic evaluator → OR-Tools GLOP**. React and TypeScript will consume the same versioned API after the design handoff. Serve the built frontend and API from one loopback origin. The primary demo needs no external database, account, API key or paid model.

Relate owns connectivity, rule applicability, candidate discovery, dependencies and plan inspection. Python performs typed comparisons, conversions and linear optimization. Checked-in data rebuilds the graph. The application obtains each solve’s inputs from a versioned graph projection. This makes it possible to demonstrate a substantive graph change: removing a transformation rule from a test snapshot must make its candidate disappear without changing Python code.

| Graph area | Proposed entities and relationships |
|---|---|
| Dated network | `Snapshot`, `Facility`, `FacilityIdentity`, `Site`, `Stream`, `Material`, `Destination`, `Commitment`, `InstalledCapability`. Connect producer → stream → material, facility → installed capability, and stream → commitment → destination. Preserve historical names and physical transfer boundaries. |
| Process knowledge | `ProcessTemplate`, typed input/output ports, `RuleVersion`, `Requirement`, `Unit`, `Measurement`, `Permission`, `Claim`, `Source`. Templates declare accepted inputs and joint outputs. Rules specify applicability, comparisons and evidence. Permissions carry activity, material, site, issuer, state and effective dates. |
| Planning and audit | `Candidate`, `Scenario`, `Evaluation`, `Verdict`, `Plan`, `Allocation`, `ConstraintResult`. A candidate identifies a fixed process package, site and capacity. Each plan references its snapshot, candidate or baseline, scenario, rule versions, assumptions and solver manifest. Allocations and binding constraints point back to the facts that generated them. |

**Discovery procedure**

1. Use parameterized Cypher to find source materials and bounded source-to-use paths through template ports. Query installed capabilities separately at the same snapshot. Include existing direct routes. Require destinations for material coproducts as well as the desired energy product.
2. Identify missing capabilities along those paths. A single proposed installation may bundle digestion, upgrading and digestate handling if its fixed configuration explicitly supplies all three. A digester alone cannot connect raw biogas to a grid-quality biomethane consumer.
3. Instantiate the missing package against declared hypothetical sites and fixed capacity options. Enumerate every admissible combination in the small catalog. Deduplicate by package version, site and capacity, retaining all supporting paths. Aim for 3–5 alternatives. Fewer are acceptable. If two variants differ only in a nonbinding capacity, show the tie.
4. Evaluate roughly 8–12 evidence-backed rules where available. Start with material identity, required pretreatment, solids/yield basis, process acceptance, raw-gas compatibility, upgraded-gas specification, interconnection, digestate acceptance, agricultural nutrient capacity, and scoped permissions. These are research targets. Every implemented requirement needs a defined comparison or categorical predicate and a linked source or planning assumption.
5. Emit `passed`, `failed`, or `unresolved` per requirement, with stream, process, rule version, measurements, units and evidence IDs. A prohibition or failed hard requirement excludes the route. Unverified authorization preserves a **conditional opportunity**. A conditional numerical solve requires an explicitly named assumption for each missing prerequisite it relies on. The underlying unresolved verdict stays visible. Operational eligibility requires affirmative, applicable evidence.

No second graph engine, graph-server deployment, browser-owned persistent store, or LLM-authored rules. If time permits after the core demo, expose discovery, explanation and evidence inspection through local MCP tools calling the same application services.

## 4. Allocation, ranking and resilience

**Use one annual steady-state LP for the baseline and one per fixed candidate per scenario.** Annual aggregate data supports an annual planning model. The demo should expose seasonal agricultural acceptance as a limitation unless seasonal data becomes available.

| Model element | Specification |
|---|---|
| Variables and units | Nonnegative flow on each eligible physical exchange in its native unit per year. Track stream-specific processor input in wet tonnes, dry matter and volatile solids in tonnes on their stated basis, gas in standard m³ with declared reference conditions and composition, energy in MWh on a declared heating-value basis, and agricultural obligations in their contracted unit. Track unallocated source material and unmet soft demand separately. |
| Supply and commitments | Balance each source exactly across baseline deliveries, processor feed and unallocated material. Unallocated material is a reported planning shortfall with no benefit credit. Protect historical obligations. A contract requiring direct delivery remains binding. Where the original terms are unknown, run a protected case and a clearly identified alternative allowing an equivalent nutrient service through digestate. Both baseline and candidates use the same scenario terms. |
| Conversion and capacity | Use stream-specific fixed coefficients. For example, wet input × dry fraction × volatile fraction of dry matter × methane yield gives methane volume only when all bases match. Apply recovery, losses, heating value and own-use once. Cap shared intake, upgrading and downstream handling across all contributing sources. Maintain linked balances for raw gas, recovered gas, digestate, added water and documented losses or separation outputs. Reject inconsistent units or unexplained mass residuals beyond the declared tolerance. |
| Destinations and quality | Bound energy delivery by named offtake and interconnection capacities, and land application by mass and applicable nutrient bounds. Couple every unit of processor throughput to all its outputs. Allow a loss only through a specified coefficient and bounded physical route. Do not use unallocated feed as an outlet for already-produced digestate. Exclude cycles at model compilation and enforce one physical variable per shared exchange regardless of how many graph paths use it. |
| Objective | Honor hard commitments first as feasibility constraints. Among feasible allocations, maximize annual **net useful energy**: accepted final energy delivery less modeled external process and transport energy, using MWh throughout and a consistent boundary for baseline and candidates. Account for internally consumed gas before delivery. Where energy coefficients are missing, use explicit scenario assumptions or switch the **entire comparison** to delivered biomethane MWh/year and label the narrower metric. |
| Ties and comparison | Within a recorded numerical tolerance, minimize unallocated wet feed, then transport work on comparable freight legs in tonne-km. Canonicalize any remaining equivalent flow allocation by stable exchange ID for reproducible explanations. Keep materially tied candidates tied. Compare baseline and every candidate under identical inputs. Favor retaining the baseline when an optional addition yields no improvement. Publish no financial ranking in the MVP. |
| Status | Rank only validated optimal solutions. Show infeasible, unbounded, numerical failure and incomplete solve as distinct states. An unbounded result is a model defect. Check residuals and bounds independently. For infeasibility, identify conflicting fixed bounds when provable or run a separately labelled diagnostic relaxation. Never publish relaxed allocations as feasible plans. |

An optional processor can sit idle. Under identical constraints and zero fixed burden its best objective therefore cannot be worse than the baseline. Test baseline preference on a tie, and separately test a strictly better baseline using a fixture with a documented fixed annual energy draw for the installed candidate. Keep fixed burdens explicit. Do not add them to the historical case solely to create a losing option. If minimum-on/off operation or nonlinear yields become essential, first split them into a small set of externally fixed operating cases. Escalate to a mixed-integer model only if the decisions genuinely must be optimized jointly.

**Stress tests.** Re-solve each candidate and the baseline after each supplier is removed and under a configurable processor capacity reduction, initially 50% as a labelled demonstration setting. Removal sets that supplier’s available feed to zero. Preserve destination obligations unless their recorded terms make them supplier-contingent. Apply a reduction only to its targeted processor.

Show unstressed and stressed outcomes, deltas against the same plan before disruption and against the baseline under the same disruption, changed allocations, unallocated feed, unmet demand, and active constraints with units. Omit percentages for a zero denominator. Identify the worst supplier removal, including ties and infeasible outcomes. A substitute route earns an allocated volume only from a re-solve. To claim additional substitutable capacity, run a bounded auxiliary LP maximizing that route while maintaining the reported service level. Distinguish **reachable**, **eligible under the scenario**, and **allocated** throughout.

Rank by the normal-case objective; show worst tested performance alongside it. Where the normal-case and disruption leaders differ, name both and show the trade-off. Avoid an unexplained composite resilience score.

## 5. API, functional views and mandatory design handoff

Use `/api/v1` with immutable snapshot references. Quantities carry `value`, `unit`, `basis`, and `period`. Shared responses distinguish assumptions, open requirements, historical facts, and solver status.

| Operation | Response and user action |
|---|---|
| `GET /snapshots/{id}/network` | Explore dated facilities, streams, existing destinations, commitments and capability gaps. Select a node or edge to inspect its physical meaning and evidence. Provide an equivalent keyboard-accessible list. |
| `GET /snapshots/{id}/candidates` and `GET /candidates/{id}` | Inspect discovered configurations, supported paths, site/capacity assumptions, required coproduct outlets and rule verdicts. Expand a failed or unresolved condition to the exact measurement or missing fact. |
| `POST /evaluations` | Accept a snapshot ID, permitted candidate IDs, an assumption-set ID and typed disruptions. Include the baseline automatically. Return a persisted evaluation ID and plan IDs. Identical input fingerprints reuse the completed result. Reject invalid IDs, mismatched snapshots and capacity fractions outside `[0,1]`. |
| `GET /evaluations/{id}` and `GET /plans/{id}` | Compare candidates and baseline, inspect ties, annual quantities, absolute/percentage changes, worst removals, changed exchanges, constraint slack and solver status. Show why a candidate could not be scored. |
| `GET /evidence/{id}` | Show value, classification, unit, effective period, publication/access dates, source locator, derivation and dependent rules/plans. The evidence view also shows where an assumption changes the recommendation. |

**Functional design package:** network explorer, opportunity detail, baseline/candidate comparison, disruption analysis, and shared evidence detail. Evidence detail can be a panel in the supplied design. Provide representative API payloads from the working backend, action/state maps, network selection and filtering behavior, scenario controls, and examples of loading, empty, error, conditional, infeasible, tied and zero-change states. Include a case where direct agricultural use continues after a supplier disruption.
